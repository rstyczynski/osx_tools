= TimeMachine Simplified (tms)

Version 1.6.0. Bash functions for full and incremental directory backups.

== Setup

Requires Bash 3.2 or newer, Python 3.9+ at `/usr/bin/python3`, GNU coreutils (`gcp` and `realpath`), and a modern
rsync supporting `--info=progress2`. On macOS:

[source,bash]
----
brew install coreutils rsync
source ~/projects/osx_tools/tms/tms.sh
backup_volume=/Volumes/Backup
----

Keep the source command and destination setting in the interactive section of
`~/.bashrc`. Ensure the Homebrew tools are on `PATH`.
The destination filesystem must support hard links and symbolic links.
If unset, `backup_volume` defaults to `/Volumes/Backup`.

== Commands

[source,bash]
----
tms                         # Show help and current backup_volume; no backup
tms --help
tms --version
tms ~/Documents             # First full backup, then incremental snapshots
tms ~/Documents full        # Force a full snapshot
tms --all                   # Back up all sources already known at this destination
tms --sources               # List known sources, states, sizes, files, and last backup
tms --explain ~/project/.models/weights.bin --source ~/project
----

Every invocation displays the effective `backup_volume`.
Each source has a visible divider and a header showing its path and destination.
After completion, a final report has one row per source: source path, status
(`OK`, `FAILED`, or `SKIPPED`), changed files, excluded files, backup type, elapsed seconds,
and snapshot name or failure/skip note. Batch runs print one combined report.
Changed files means regular files actually transferred by rsync; a full backup
counts all transferred regular files. A dash means the count is unavailable.
On a failed transfer, any reported count is partial. Transfer statistics are
retained beside the snapshot in `<timestamp>[.full].stats`.
`--all` is explicit: merely running `tms` never starts a batch backup.
`--all` takes no additional arguments and runs each source sequentially.
Missing or unrecognizable sources are reported; the other sources still run.
The command returns nonzero if any source fails or is skipped, or no sources are known.

=== Source inventory

`tms --sources` prints one row per destination label with its original source,
state, size, regular-file count, and last successful backup (`latest`). It does
not start backups or change snapshots. Source discovery also supports legacy
snapshots without `.source` metadata.

States are `READY`, `MISSING`, `UNKNOWN` (original path cannot be recovered),
`NO-BACKUP` (source exists but there is no successful `latest` snapshot), and
`UNREADABLE` (size or file enumeration failed). Unavailable fields show `-`.
Size is allocated source disk usage from `du`, expressed in KiB/MiB/GiB;
file counts include regular files. Scans do not follow symbolic links and may
take time on large directory trees. The inventory command succeeds even when
rows show unavailable sources; a missing backup root is an error.

== Central exclusions and local overrides (1.6.0)

The central policy is `~/.config/tms/excludes`. It contains one rule per line.
Installation/explicit setup creates this file only if missing; user edits and
intentionally empty files are preserved. If the file is missing, TMS reads the
bundled `excludes.default` with the same defaults:

[source,text]
----
.build/
.models/
.terraform/
.cache/
hf-cache/
supertonic-cache/
----

Only directories with these names and their descendants are excluded. There is
no broad `*cache` rule, no automatic use of `.gitignore`, and no default exclusion
for Git history, Terraform state files, recordings, or arbitrary `local-data`.
Excluding `.terraform/` skips its local initialization/backend metadata as well
as provider downloads; keep actual state files and dependency lockfiles backed up.
Use `TMS_EXCLUDES_FILE=/absolute/path` to select a different central policy.

=== Local rules and precedence

Place `.tmsignore` in a project or subdirectory. Rules are data, never shell code.
TMS applies central rules first, then local files from ancestor directories down
to the entry's parent directory. The last matching rule wins. Sibling projects'
local rules do not affect one another.

[source,text]
----
# Additional exclusions in this project:
generated-downloads/
temporary-exports/

# Keep a locally trained model despite the central .models rule:
!/.models/my-trained-model/

# Or use !/.models/ to keep the whole directory.
----

* `!` means include; a normal rule means exclude. Blank lines and `#` comments are ignored.
* Rules are case-sensitive. Names without `/` match at any depth beneath the rule file.
* A leading `/`, or a pattern containing `/`, anchors the match to that rule file's directory.
  Central anchored paths are relative to the selected backup source root.
* A trailing `/` restricts a rule to directories and their descendants; it does not exclude a same-named ordinary file.
* `*`, `?`, and character classes match within one path component; a `**` component matches zero or more directory levels.
* Escape an initial `#` or `!` with a backslash for a literal filename. Surrounding rule whitespace is trimmed.
* Excluded parents are still traversed to discover nested overrides. Necessary parent
  directories are retained for explicitly included descendants.
* The explicitly selected source root, `.tmsignore` files, and the central rules
  file when within the source are always retained, even if a rule would exclude them.

The filter examines filesystem metadata, not file contents. Finding nested rules
and counting excluded entries still requires walking excluded directory trees;
large build caches can therefore take time to scan even though their data is not copied.

=== Explain a decision

[source,bash]
----
tms --explain ~/project/.models/my-trained-model/weights.bin --source ~/project
----

This read-only command prints INCLUDED/EXCLUDED, source root, the winning rule,
and its configuration file and line number. If `--source` is omitted, TMS chooses
its longest matching registered `.source` root, then a containing Git root, then
a containing `.tmsignore` directory, then the path's directory. The chosen root
is printed; use `--source` to reproduce a particular backup context exactly.
An excluded directory may still exist structurally to contain included descendants.

=== Incremental snapshots, counts, and policy recovery

Rules apply to full, incremental, single-source, configuration-file batch,
`--all`, scheduled, and menu-triggered backups. A newly excluded entry carried
from the previous snapshot is unlinked only from the new snapshot. Source files
and entries in older snapshots are not deleted. Existing snapshots do not shrink.
A newly included unchanged file is copied if it is absent from the new snapshot.
New included empty directories are also captured.

`EXCLUDED` counts unique excluded non-directory paths found in the current source
or removed from the new carried snapshot; a path present in both is counted once.
The value is shown per source in terminal and email reports. It is a path count,
not bytes saved or the number of directories. A dash means the scan did not finish.

Each successful snapshot has a NUL-delimited `<timestamp>[.full].files0` manifest
and a `<timestamp>[.full].rules.json` sidecar with the full active central/local
configuration text, origins, and counts. NUL delimiters support embedded newlines
in filenames. `.tmsignore` files in the source are also included in the file tree.
`tms_restore` copies the sidecar to `tms-exclusions.json` in the new restore
location. Consult it to recover the central/ancestor rules; restoration does not
overwrite your currently active policy automatically.

Unreadable directories/configuration and malformed rules fail the backup rather
than silently omitting data, and do not advance `latest`. The backup destination
must be outside the source directory. Rules do not rewrite or remove excluded
files that are already stored as objects in Git history.

== Optional agent-assisted source review

TMS provides a portable review guide for the user's own agentic layer. It does
not call an AI service or start an autonomous review. Point your preferred agent
at link:agent-review/AGENTS.md[the agent review instructions] and select one of
link:agent-review/PROMPTS.md[the six example prompts]. Substitute the actual TMS,
backup-source, and project paths before using a prompt.

The guide requires reading the installed TMS documentation, establishing how
large inputs can be recovered, distinguishing reproducible downloads/build data
from unique source/results, and inspecting existing exclusion rules for accidental
omissions. It covers scoped local overrides, concrete configuration proposals,
`--explain` verification with the actual source root, and rollback for authorized
edits. It also requires keeping recovery manifests and revisions available.

Start with the read-only discovery or project-proposal prompt. An agent should
apply rules only when the user has authorized that scope. The apply prompt accepts
an exact approved patch and does not authorize cleanup, Git history changes,
remote pushes, scheduler changes, or production backups. Audit output must
separate estimated future backup-input reduction from reclaimed source/snapshot space.

Reference the guide from your existing agent instructions if useful:

[source,text]
----
When explicitly asked to review TMS backup-source optimization, also read
/path/to/osx_tools/tms/agent-review/AGENTS.md and follow the installed TMS docs.
----

Keep the project's existing instructions intact. The guide is opt-in and scoped
to requested source analysis; placing it in a subdirectory does not automatically
activate it in unrelated projects. No particular agent vendor or model is required.

== Destination layout and discovery

Snapshots live in `backup_volume/backup/<source-basename>/<timestamp>[.full]`.
Each snapshot preserves the absolute source path below its root.
`latest` points to the last successful snapshot. Failed copies do not advance it.
Snapshots created within the same second cannot overwrite an existing snapshot.

Successful backups record their absolute source path in the label's `.source` file.
For older backups, `--all` recovers that path from `latest`, or a timestamped
snapshot if `latest` is absent. Empty or ambiguous layouts are skipped.
If a recorded source has moved, it is reported as missing.
Labels with `.source` metadata reject a different source with the same basename.
Use distinct basenames for different backup sources.

Incremental snapshots retain files deleted from the source; deletions are not
mirrored. Inspect the chosen snapshot when selecting files to restore.

== Restore

[source,bash]
----
tms_restore Documents 2026-11-12T130000.full /Volumes/Data/Restore
----

The restore directory must not already exist. The selected snapshot is copied
into that directory, retaining its stored absolute-path tree.

== Limitations and known correctness bugs

The following metadata behavior and correctness bugs were checked on macOS with
GNU rsync 3.4.1 on 2026-11-12 using temporary full-backup, restore, and incremental
cycles. The two correctness bugs remain in version 1.6.0. Version 1.6.0 adds
policy filtering and captures new included empty directories; it does not repair
historical metadata or the rsync content quick-check bug.

=== Metadata fidelity

[cols="1,3",options="header"]
|===
|Metadata |Current behavior
|File modification date (`mtime`)
|Preserved by `rsync -a`, including during restore; it is not generally reset to copy time.
|Unix permission bits
|Preserved on a full backup and restore. See the shared-snapshot metadata bug below.
|Owner and group
|Requested by `rsync -a`, subject to the user's privileges and the target filesystem; arbitrary ownership is not guaranteed.
|Original creation date (birth time)
|Not explicitly preserved. In the test, a file created in 2000 and modified in 2001 was restored with a 2001 creation date.
|Metadata-change time (`ctime`)
|Filesystem-managed; changes during copying and metadata updates rather than restoring the source value.
|Access time (`atime`)
|Not explicitly preserved; reading files can itself update it.
|Access control lists (ACLs)
|Not preserved by the current rsync flags; the test's additional ACL was lost.
|Extended attributes and macOS-specific metadata
|Not preserved by the current rsync flags; a custom extended attribute was lost. Finder tags and resource-fork metadata must not be assumed to survive.
|===

Archive mode alone does not enable rsync's ACL, extended-attribute, access-time,
creation-time, or source-hard-link preservation options. See the
https://www.samba.org/ftp/rsync/rsync.html[rsync archive-mode documentation].
Metadata omitted during backup cannot be recovered merely by changing restore options.

=== Filesystem layout and restore behavior

* *Deletions are not mirrored.* A file deleted from the source remains in later
  incremental snapshots. A snapshot can therefore contain files no longer in the source.
* *Existing directory-only metadata changes can be missed by incremental selection.*
  New included directories are captured, but an existing directory is not selected
  solely because its metadata changed.
* *Symbolic links are dereferenced.* Backup uses `--copy-links`; the restored
  test symlink was an ordinary file containing its target's data, not a symlink.
* *Original hard-link relationships are lost.* Two source filenames sharing
  one inode were restored as independent files. Hard links used between TMS
  snapshots are a separate storage optimization.
* *Restore copies a tree.* It requires a new destination and copies the selected
  timestamp directory, including the stored absolute-path hierarchy. It does
  not restore directly over the original source or provide a complete macOS
  system/Time Machine restore.

=== Known correctness bugs

* *Changed contents can be missed.* Existing regular-file discovery uses `ctime`, but
  rsync subsequently uses its default size/mtime quick check. A same-length edit
  with the original modification date restored was selected for processing yet
  skipped by rsync: the source contained the new text while the new backup
  still contained the old text. A successful run or zero transferred files is
  therefore not proof that source contents are identical.
* *Historical snapshot metadata can change.* Incremental snapshots initially
  share file inodes through hard links. Applying a later permission-only update
  can modify metadata shared with earlier snapshots. In the test, changing a
  source file from mode `0640` to `0600` and backing it up also changed the
  original full snapshot's file mode to `0600`. Snapshots are not immutable
  records of historical metadata.

These two findings are backup-correctness defects requiring implementation
changes, not merely display or reporting limitations.

== File-based batch configuration

The existing `tms_batch [config_file]` command remains available.
It reads source directories, one per line, from `~/etc/tms_config` by default.
Blank lines and lines beginning with `#` are ignored. Relative paths are resolved
from the current working directory. Use `tms --all` for destination-based discovery.

== macOS scheduler, SwiftBar, and access controls (1.5)

All setup is scripted and requires explicit arguments. First load the functions:

[source,bash]
----
source ~/projects/osx_tools/tms/tms.sh

# Native launchd schedule; independent of SwiftBar:
tms --scheduler status       # Also the default for --scheduler; --scheduler check is an alias
tms --scheduler on
tms --scheduler off

# Menu-bar plugin; does not enable or disable the scheduler:
tms --swiftbar status
tms --swiftbar on
tms --swiftbar off

# Prepare the TMS app, open the privacy panel, and print exact grant instructions:
tms --access setup
# Verify real background access under the TMS app identity (no backup/email):
tms --access status
----

`on` and `off` are idempotent. Scheduler status is read-only. SwiftBar status
means the TMS plugin symlink is installed; SwiftBar itself must be running to
show it. `--swiftbar on` opens the existing SwiftBar app and installs the plugin
in its configured directory. `off` removes only TMS's own symlink, preserving
other plugins, snapshots, logs, and configuration. The typo `--switfbar` is
accepted as an alias. Status also accepts `check`.

The compatibility script `python3 install-service.py scheduler on` exposes the
same controls. Running it without a feature/action does not install anything.
Turning the scheduler on does not install SwiftBar; turning SwiftBar on does
not enable the schedule. Setup preserves existing user configuration and does
not rewrite `.bash_profile` or embed a recipient address.

=== Native schedule

The per-user LaunchAgent `local.tms.backup` runs at 00:00, 04:00, 08:00, 12:00,
16:00, and 20:00 in the Mac's local timezone. `StartCalendarInterval` catches up
once on wake if the machine slept through a scheduled time. The user must be
logged in; jobs missed while powered off do not catch up. No cron job is used.

`tms --scheduler on` builds the helper if needed, writes the LaunchAgent,
enables it, and loads it without immediately starting a backup. `off` persists
launchd's disabled state across reboots and unloads the job. If a scheduled
backup is currently running, changes are refused until it finishes so no
backup is interrupted. Manual backup-now actions remain available while the
scheduler is off. Status reports enabled/disabled, loaded/runtime state, actual
configured hours and timezone, the next expected run, and the plist path.

The agent is stored at `~/Library/LaunchAgents/local.tms.backup.plist` and the
launcher at `~/Applications/TMS Backup.app`. The launcher is built from
`TMSBackup.swift` and ad-hoc signed locally; no software is downloaded. Unchanged
launchers are retained so repeated `on` commands preserve their privacy identity.

=== Full Disk Access: one manual macOS grant

macOS does not permit a normal script to grant Full Disk Access. TMS automates
building the dedicated app, opening the correct settings panel and Finder, and
verifying access; the final privacy grant must be made by the user:

. Run `tms --access setup`.
. In System Settings -> Privacy & Security -> Full Disk Access, click *+*.
  Authenticate if macOS requests it.
. Press *Command-Shift-G*, enter `~/Applications/TMS Backup.app`, and add it.
  Alternatively, drag the app from the Finder window into the access list.
. Turn the *TMS Backup.app* switch *ON*. Do not grant Bash, Python, or cron access.
. Run `tms --access status`. Expect *READABLE* for Documents, the destination,
  and all known source directories, followed by *Access check: PASS*.

The access check uses a temporary native LaunchAgent with the actual TMS app
identity, reads directory metadata only, and removes the test agent afterward.
It does not run backups or send emails. Missing sources also cause a failed
check and are named in its output. If the app is rebuilt or the repository is
moved, rerun the check and renew the grant if macOS requires it. If prompted,
allow TMS Backup to control Mail for report submission as well.

=== Destination and email

New configuration defaults to the current `backup_volume` when enabling from
`tms`, or `/Volumes/Backup` if none is set. It is saved in
`~/.config/tms/config.json`; existing files are preserved. Set `backup_volume`
there for future background runs, and optionally `mail_from` for the sender.

Add your report recipient to the noninteractive login environment:

[source,bash]
----
# In ~/.bash_profile:
export TMS_REPORT_EMAIL="you@example.com"
----

`tms-run.sh --all` loads `.bash_profile`, explicitly sources `tms.sh`, and runs
`tms --all`. It never sources interactive `.bashrc`. It also accepts
`--source /absolute/path` for a single source. A kernel file lock prevents two
wrapper runs from overlapping and releases on exit or crash. Direct calls to
`tms` bypass the wrapper lock.

Emails use Apple Mail rich text (HTML with a plain-text alternative), Courier
at 11 points with a bold heading, an overview of totals, and
a compact aligned table. Common source-directory prefixes appear once above the
table; full paths remain in the unmodified plain-text summary and logs. The
formatted email body is retained alongside the summary as `.summary.email.txt`.

Each completed run submits its final per-source summary through the already
configured Apple Mail account. No SMTP passwords are stored by TMS. Emails
include scheduler enabled/loaded/runtime state, configured hours/timezone,
next expected run, and wake behavior, even for manual runs while scheduling is
disabled. Failures and missing final reports are emailed too. A Mail submission
confirms queuing, not delivery. The logged-in user's account and Automation
permission must be available; this is not a pre-login email service.

For an explicit setup email without running backups:

[source,bash]
----
~/Applications/"TMS Backup.app"/Contents/MacOS/TMSBackup --test-email
----

=== Menu and logs

SwiftBar refreshes every minute. It shows running/success/failure state, last-run
time, actual scheduler status, mail status, destination, and last-backup timestamps.
Use *Back up all now* or a source's *Back up now* submenu. Other actions open the
saved summary and logs. Source paths and timestamps are cached after each wrapper
run or setup test, so SwiftBar does not need Full Disk Access itself.

Logs and emailed summaries are private files under `~/Library/Logs/tms/`; status,
cached sources, and the latest summary are under `~/Library/Application Support/tms/`.
Logs are retained until manually removed. Inspect `launchd-error.log` and menu
mail status if a background run fails. `/usr/bin/python3`, Swift tools for the
initial helper build, existing SwiftBar, and configured Apple Mail are required.

To stop automatic operation, run `tms --scheduler off` and `tms --swiftbar off`.
The helper, access grant, snapshots, settings, and logs remain for reuse.

=== Service tests

`python3 -B test-manage.py` tests independent on/off/status transitions and
background-check cleanup with mocked macOS commands. `python3 -B test-service.py`
tests wrapper backups, summaries with scheduler status, cached menu actions,
locking, and email error reporting using temporary sources and mocked mail.
Neither test suite touches the real scheduler or sends email.

Run `python3 -B test-excludes.py` for rule precedence, snapshot filtering, override
re-inclusion, filename handling, policy recovery, and explanation tests.
